Problem Statement

Property managers often rely on separate tools for managing properties, units, leases, residents, rental applications, rent schedules, payments, documents, and notifications. This creates duplicate work, incomplete records, weak communication with tenants, and limited visibility into the financial and operational status of rental properties.

Abstract

This project presents a multi-tenant property management platform designed to support property management companies, administrators, property managers, applicants, and residents through one integrated system. The platform allows companies to manage properties and units, publish available units for browsing, receive rental applications, approve or reject applicants, create draft leases, manage resident lease details, generate rent payment schedules, record payments, issue receipts, and send email notifications. The system follows an object-oriented design and is implemented as a web application using Laravel for the backend, React for the frontend, PostgreSQL for persistent storage, Redis for queues and sessions, and Docker for deployment. The report describes the system requirements, main UML design areas, implementation approach, testing methods, achievements, risks, and references.

Introduction

The selected topic is a Property Management Platform for rental businesses that need to manage multiple properties, units, residents, and applications under different companies. The system is relevant because rental management involves repeated business processes such as unit listing, tenant application, lease creation, rent tracking, receipt generation, and communication between managers and residents. The project demonstrates system analysis and design concepts by converting these real business processes into functional requirements, non-functional requirements, database entities, object-oriented services, user roles, workflows, and UML diagrams. The final implementation provides a practical web-based solution where public users can browse available units, applicants can apply, managers can review applications, and residents can view their leases and payment information.

Analysis

System Actors

Actor Description
Super Admin Platform-level owner who can manage all companies and platform metrics. This actor is planned for future enhancement.
Admin Company owner or main administrator with full access to company properties, units, leases, applications, payments, documents, reports, and settings.
Property Manager Company employee responsible for managing assigned properties, reviewing applications, recording payments, and monitoring leases.
Applicant Public registered user who browses properties and submits rental applications.
Resident Tenant with an approved application and lease who can view lease details, deposits, payments, receipts, and personal applications.
Maintenance Staff User who handles maintenance requests. This role is designed but the full maintenance workflow is deferred.

Functional Requirements

  1. The system shall allow companies to register and manage their own data separately from other companies.
  2. The system shall allow admins and property managers to create, edit, and view properties.
  3. The system shall allow admins and property managers to create, edit, and view units under a property.
  4. The system shall allow property and unit photos to be uploaded and displayed on public browsing pages.
  5. The system shall allow public users to register as applicants.
  6. The system shall allow logged-in applicants and residents to browse available properties and units.
  7. The system shall allow applicants to submit rental applications for available units.
  8. The system shall prevent duplicate pending applications for the same applicant and unit.
  9. The system shall allow admins and property managers to review applications.
  10. The system shall allow admins and property managers to approve an application and create a draft lease.
  11. The system shall allow admins and property managers to reject an application with a reason.
  12. The system shall send notification emails when an application is submitted, approved, or rejected.
  13. The system shall allow lease creation, editing, activation, termination, and renewal.
  14. The system shall generate payment schedules when a lease becomes active.
  15. The system shall allow payment recording and receipt generation.
  16. The system shall allow residents to view their leases, deposits, upcoming payments, payment history, and receipts.
  17. The system shall allow admins and property managers to view dashboards, reports, documents, and settings pages.
  18. The system shall prevent more than one active lease for the same unit.
  19. The system shall support queued background jobs for email notifications and scheduled tasks.

Non-Functional Requirements

Requirement Description
Security The system must protect private data using authentication, role-based access control, company-based data separation, and authorization policies.
Reliability Important operations such as application approval, lease creation, and photo upload should use database transactions where needed.
Usability The interface should be clear for admins, managers, applicants, and residents, with separate dashboards and role-specific navigation.
Performance The system should use efficient database queries, eager loading for relationships, Redis caching and queues, and pagination or filtering where needed.
Maintainability The backend should separate controllers, services, requests, resources, models, jobs, and policies to make the code easier to update.
Scalability The multi-tenant structure should support multiple companies in one shared database, and queued jobs should support asynchronous processing.
Availability The application should run in Docker containers and be deployable to a cloud server.

Design

Architecture Design

The system uses a client-server architecture. The frontend is a React single-page application that communicates with the backend through REST API endpoints. The backend is built with Laravel and contains controllers, services, form requests, API resources, models, policies, commands, and queued jobs. PostgreSQL stores relational data such as companies, users, properties, units, leases, rental applications, payment schedules, transactions, documents, and deposit transactions. Redis is used for queues, cache, and sessions. Laravel Horizon monitors queued notification jobs. Docker containers are used for the application, web server, PostgreSQL, Redis, and Horizon.

Database Design Summary

The database follows a shared multi-tenant model using company identifiers. The companies table owns properties and leases. The company_users pivot table links users to companies and stores company role information. Properties contain units. Units are connected to rental applications and leases. Leases store dates, financial terms, deposit information, status, and relationship to the resident and unit. Payment schedules are generated from active leases and payment transactions record actual payments. Documents use a polymorphic relationship so files can belong to leases, transactions, properties, units, users, or maintenance requests. Rental applications store applicant income, employment information, references, review status, rejection reason, review date, and reviewer.

Implementation

The system was implemented as a full-stack web application. Laravel 11 was used for backend development because it provides routing, authentication support, validation, database migrations, Eloquent ORM, queues, policies, resources, and scheduled commands. React was used for the frontend because it supports component-based user interfaces and client-side routing. PostgreSQL was selected as the main database because it supports strong relational integrity and constraints. Redis was used for queues, cache, and sessions. Docker was used to keep the development and deployment environment consistent.

The backend code is organized by responsibility. Controllers receive API requests and delegate business logic to service classes. Form request classes validate input before data reaches the service layer. API resources format responses for the frontend. Jobs handle queued email notifications. Models define database relationships. Policies and middleware protect restricted routes. This separation supports maintainability and makes the system easier to test.

Important implemented modules include property and unit management, public property browsing, applicant registration, rental application submission, application review, lease management, payment schedule generation, manual payment recording, receipt generation, deposit tracking, resident lease views, dashboards, reports, document listing, settings pages, and email notifications. The system also includes safeguards such as preventing active lease duplication for a unit and excluding property and unit photos from the general documents page.

Testing Methods

The project uses several testing methods. Functional testing verifies that each main workflow works from start to finish, such as registering an applicant, browsing available units, submitting an application, approving it, creating a draft lease, activating a lease, generating payments, recording a payment, and viewing resident lease details. Validation testing checks whether required fields, numeric values, file uploads, and application forms reject invalid input. Authorization testing checks whether admins, property managers, applicants, and residents can only access the routes allowed for their roles. Database testing verifies constraints such as preventing duplicate active leases and filtering records by company. Queue testing verifies that notification jobs are dispatched and processed correctly by Redis and Horizon. UI testing verifies that pages render correctly in the browser, images appear in public browsing pages, and dashboards use real backend data instead of static data.

Results and Achievements

Accomplishments

The project produced a working property management platform with clear role separation and real business workflows. Applicants can browse properties and units, apply for available units, and view their own applications. Admins and property managers can review applications, approve them into draft leases, or reject them with a reason. Residents can view their dashboard, leases, deposits, payment schedules, payment history, and receipts. The platform supports property and unit photos, public browsing, application notification emails, lease lifecycle management, scheduled payment generation, receipt generation, dashboards, reports, and documents.

Added Values

The system adds value by centralizing processes that are normally separated across spreadsheets, email, file folders, and manual reminders. It improves visibility for managers and gives residents direct access to their own lease and payment information. The multi-tenant design also allows many property management companies to use the same platform while keeping their data separated.

Risks

Main risks include incorrect permission configuration, incomplete email delivery setup, file storage limitations, and future payment processing complexity. Stripe integration is planned but deferred, so online payment processing is not yet part of the current implementation.

Advantages and Disadvantages

The main advantages are organized workflows, reusable backend services, role-based access, queued emails, public browsing, and a scalable multi-tenant foundation. The disadvantages are that the system requires careful configuration of mail, queues, storage, and deployment, and some advanced features such as maintenance workflows, super-admin billing, and Stripe payment processing are still future work.

Conclusion

The Property Management Platform demonstrates how system analysis and design concepts can be applied to a realistic rental management problem. The system identifies the major actors, requirements, entities, workflows, and components needed for property management, then implements them using a modern object-oriented web application architecture.

The project is successful because it provides a working foundation for managing properties, units, applications, leases, payments, documents, and notifications. Future improvements can include Stripe Connect payment processing, maintenance request workflows, advanced analytics, super-admin subscription billing, and cloud object storage. These additions can build on the existing design without changing the main architecture.
